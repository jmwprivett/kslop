### What has NOT been tried — Quest 1

1. **No physical run of the identity canaries.** Zero recorded results for `CNDPhysicalPACIdentityCanary` / `CNDPhysicalPACCrossTaskCanary` in docs/, logs/, or any report path I can find. The VM result is explicitly restricted to the developer-enabled vPhone; stock-boot delivery is the open question and nothing has answered it.
2. **No physical TaskRop integration of the converter.** `Thread.m` exposes `thread_convert_sign_state_for_target` (fail-closed), but production `sign_state` still uses `EXCEPTION_STATE` (no thread port). The documented next boundary — `EXCEPTION_STATE_IDENTITY` plumbing — is designed, not wired.
3. **No arm64e kernel signing-gadget hunt (Fugu15/jb3 class).** `rea-exploit-research.md` *proposes* scripted REA sweeps for `blraa`-reached functions, `xkr` key misuse, and "kernel function that signs pointers for you" over `__TEXT_EXEC`, kexts (`AppleAVE`, AO, USB), IOKit user clients, and `IOExternalMethod` tables. Nothing in the tree or docs shows that sweep was actually run on the 23A341 physical kernelcache. This is the classic kcall enabler and it is a listed idea, not a performed experiment.
4. **No `pmap_sign_user_ptr` against kernel-keyed targets.** Confirmed services cover IA/DA user-pointer keys under a user JOP context; nobody has yet tested (even on the VM) how far the selected-context trick can be pushed toward kernel data-pointer PAC (the exact thing `ip_kobject` needs). The docs correctly note the mismatch — but the *boundary* was not probed, only asserted.
5. **No writable-kernel-data kcall-via-vtable/dispatch-slot.** You now have physically proven aperture writes to shared-cache data pages *and* ordinary `kwrite32` kernel data writes. A data-only kcall (overwriting a legitimately called, kernel-`DATA`-PAC'd function pointer slot) has not been attempted; nothing in the docs rules it in or out. On arm64e heap pointers are signed, but *which* dispatch tables live in writable kernel data on 23A341 has not been surveyed.
6. **No `sysctl`/IOKit/IOExternalMethod target survey on the physical kernel.** The runtime closed the AMFI query selector-6 hit and the negative entitled-load boundary (correctly stopped at the policy line), but the broad "validated-but-weak call target" census REA is meant to automate has not been done.
7. **No SPTM write primitive or PPL-level research.** Acknowledged as a separate bug class; nothing attempted (fair, but it belongs on the "not tried" list, not the "impossible" list).
8. **No trust-cache route beyond observation.** TXM gateway (op `0x0c`, seven arguments, dispatcher `0xfffffff01702ae80` → adapter `0x...2b6f4` → load handler `0x...02627c`) is static-closed; the natural entitled-load capture is still pending; no holder of `com.apple.private.amfi.can-load-trust-cache` was found in the scan (also not tried: observing a *legitimate* load from a system event such as a Mavericks-style install, or auditing whether the entitlement can be legitimately obtained).
